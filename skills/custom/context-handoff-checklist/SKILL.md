# Context Handoff Checklist

生成一份**足以完成任务、又不过量倾倒上下文**的交接包。交接内容必须区分事实、推断和待验证假设，并让接收方能够定位代码、数据和实验依据。

共享记录约定见 `../_shared/RESEARCH_ARTIFACT_CONTRACT.md`。

## 适用范围

在以下情况使用：

- 将代码审查、调试、实验分析或实现任务交给子 Agent；
- Claude Code、Codex、Gemini 等模型之间传递任务；
- 长任务跨会话继续；
- 接收方无法直接访问完整历史，或历史中存在关键约束与失败尝试。

以下情况不使用：

- 问题可在一条消息中完整表达；
- 接收方已经读取同一仓库、同一提交和同一实验记录；
- 只是询问通用知识，不依赖项目状态。

## 核心原则

1. **交付证据，不只交付摘要。** 涉及代码、日志或数据时，给出文件路径、行号、提交、运行编号和原始结果位置。
2. **按任务裁剪。** 不把整个项目历史复制给接收方，只保留会影响结论或操作范围的信息。
3. **区分证据状态。** 明确标记已确认事实、基于证据的推断、未验证假设和用户决定。
4. **声明操作边界。** 说明允许读取和修改的文件、禁止事项、预算及是否可以执行实验。
5. **先确认理解，再执行。** 接收方应先复述任务、关键假设和缺失信息；只有理解一致后才继续非平凡修改。
6. **外部发送最小化。** 向外部模型发送材料前确认用户授权，删除密钥、隐私和未授权原始数据，只发送完成任务所需的最小证据包。

## 交接前的上下文核对

1. 读取 `.research/state.md` 或项目中的等价状态文件。
2. 核对 state 的更新时间、branch、commit、dirty 状态、`last_checkpoint_event`、`last_context_event` 和活跃证据。
3. 新会话恢复、状态冲突或新鲜度不明时，先提示用户调用 `/research-context-checkpoint open` 生成 context readback。
4. 只选择能够影响本次成功标准、操作边界或结论的内容；记录选入和省略原因。
5. 发现缺失或过期上下文时，不在摘要中补猜。将缺口及其影响显式交给接收方。

## 第一步：识别任务类型

从以下类型中选择一个主类型：

- `implementation`：实现或修改代码；
- `debugging`：定位故障或异常；
- `code_review`：审查代码、补丁或架构；
- `experiment_analysis`：分析实验数据与日志；
- `experiment_design`：设计下一轮实验；
- `research_review`：审阅研究方案、方法或证据；
- `other`：说明具体任务。

任务类型决定后续必须附带的材料。不要让所有任务填写同一份冗长表格。

## 第二步：收集共同字段

所有非平凡交接都应包含：

```markdown
## 任务
- 接收方：
- 任务类型：
- 要完成的工作：
- 期望输出：
- 成功标准：

## 当前阶段
- 项目目标：
- 当前阶段：
- 本次任务为什么现在需要做：

## 上下文检查点
- state 文件与更新时间：
- context protocol：
- 分支与提交：
- 工作区状态：
- 对应 checkpoint event：
- 最近 context event：
- 新鲜度：current|needs_refresh|unknown
- 已知过期项：

## 已确认事实
- [F-001] 事实；证据位置

## 未验证假设
- [H-001] 假设；支持迹象；替代解释

## 历史决策与失败尝试
- 已采用的决定及原因：
- 已尝试但无效的方向及证据：

## 本次选入的上下文
| 材料 | 选入原因 | 对应成功标准 | 最近检查时间 |
|---|---|---|---|

## 本次省略的上下文
| 材料类型 | 省略原因 |
|---|---|

## 已知上下文缺口
- 缺失内容：
- 可能影响：
- 接收方应如何处理：

## 约束与边界
- 允许读取：
- 允许修改：
- 禁止修改或不要做的事：
- 计算、时间或费用预算：
- 是否允许运行代码或实验：

## 返回要求
- 结果格式：
- 必须附带的检查或证据：
- 仍不确定的内容如何标记：
```

缺失但不影响任务的字段写 `unknown`。缺失信息会显著改变结论、实现路径或风险时，先向用户询问；不要自行补齐。

## 第三步：按任务类型补充材料

### 实现或代码审查

```markdown
## 代码状态
- 仓库：
- 分支：
- 提交：
- 工作区是否有未提交修改：
- 相关文件与位置：
- 当前测试命令及结果：
- 预期保持不变的行为：
```

不要只写“查看 `xxx.py`”。指出关键函数、类、配置或具体行段。

### 调试

```markdown
## 故障材料
- 复现步骤：
- 完整报错或异常现象：
- 期望行为：
- 实际行为：
- 首次出现的版本或提交：
- 已尝试的排查：
- 日志与产物位置：
```

删除密钥、令牌和隐私数据，但不要删掉错误上下文。

### 实验分析或设计

```markdown
## 实验材料
- 研究问题：
- 基线与比较条件：
- 数据集和划分：
- 指标定义：
- tuning ID、规格路径与 hash：
- config ID、trial ID 与调优阶段：
- 运行编号：
- 代码提交与配置：
- 原始结果位置：
- 当前结果直接支持什么：
- 当前数据尚不能判断什么：
```

调优任务只引用权威规格、trial 账本和运行产物，不复制整份历史表。只提供汇总数字而没有运行、配置或原始结果时，明确标记证据不完整。

## 第四步：生成交接包

默认写入：

```text
.research/handoffs/YYYYMMDD-HHMM-<recipient>-<task>.md
```

如果项目已有交接文件规范，沿用现有位置。

交接包末尾必须包含：

```markdown
## 接收确认
开始前请先回复：
1. 你理解的任务和成功标准；
2. 你将使用的主要证据；
3. 你认为仍缺失、但可能影响结论的信息；
4. 你准备修改或运行的范围。
5. 你发现的过期、冲突或无法定位的上下文。

不要在完成上述确认前进行大范围修改或高成本实验。
```

## 第五步：质量检查

发送前检查：

- 接收方能否定位关键代码、日志和结果，而不是只能相信摘要；
- 是否把推测写成了事实；
- 是否遗漏用户明确否定的方向；
- 是否说明允许修改的范围和验证方式；
- 是否包含无关的大段历史，造成上下文噪声；
- 是否泄露密钥、隐私或未授权材料；
- 当前提交、运行编号和结果是否彼此对应。
- 每项选入材料是否对应至少一个成功标准或操作边界；
- 被省略材料是否确实不会改变本次判断；
- state、handoff 和专项账本之间是否存在未声明的冲突。

任一关键项不满足时，先修正交接包。

## 收到结果后的处理

1. 对照成功标准检查结果，不以“回答看起来合理”作为完成依据。
2. 要求接收方给出引用的文件、数据、命令或计算。
3. 要求接收方分别列出“实际使用的证据”“因缺少上下文而无法判断的内容”“发现的过期或冲突上下文”。
4. 将新发现按证据状态写入 `.research/events.jsonl` 或现有实验记录。
5. 接收方因缺失上下文而误判时，追加 `context_gap` 或 `handoff_failure` 事件，再更新模板或项目状态，不只重发同一摘要。
6. 需要改变当前状态时，提示用户调用 `/research-context-checkpoint checkpoint` 统一整理，不直接把接收方意见提升为事实。

## 非目标

本 SKILL 不负责：

- 代替用户决定研究方向；
- 自动批准代码修改或高成本实验；
- 把整个聊天记录无差别转发；
- 将模型复述视为事实验证。
